# TanStack Start on Wodby

What this service adds to the Node.js service it is based on.

## Build and start

The service's Dockerfile copies the build context to `/usr/src/app`, runs `npm run build` and starts the container with `npm run start`. `package.json` must define both scripts.

- The supported production output is Nitro's Node.js server: add the `nitro()` plugin from `nitro/vite` to `vite.config.ts`, build with `vite build` and start with `node .output/server/index.mjs`. This is TanStack Start's own Node.js hosting setup.
- The Dockerfile does not install dependencies. The pipeline does it before the image is built (`wodby ci run -- npm ci`), and `node_modules` is copied with the code. Build tools such as Vite and Nitro may stay in `devDependencies`.
- `npm run build` runs while the image is built. Runtime variables of the service, including the link variables and secrets, are not available to it. Read them inside server functions, server routes or middleware at request time, not at module scope.
- The image build keeps the repository's `.gitignore` and leaves out `.git`, `.output`, `.nitro` and `.tanstack`. Keep `.output` in `.gitignore`: Tailwind CSS skips the files it lists, and without that the server build generates a different stylesheet than the client build, so a stylesheet imported with `?url` is linked under a name that does not exist. A plain `import './app.css'` in the root route avoids that in any case.
- The application must listen on port 3000. The Nitro server listens on `PORT` and defaults to 3000; leave `PORT` unset.

## Variables the service sets

| Variable | Meaning |
| --- | --- |
| `NODE_ENV` | `production` in every environment type, including `dev`. The Node.js service's `development` value for `dev` is replaced, because the container runs a production build. |
| `WORKSPACE_NODE_COMMAND` | `workspace-node vite-start`, the start command of a development workspace. |

## Linked services

The service adds no link variables. The database, mail and Redis or Valkey variables of the Node.js service apply unchanged. Server functions and server routes read them from `process.env`. They do not reach the browser: only variables prefixed with `VITE_` that exist at build time are compiled into client code.

## In a development workspace

- The application is started through Vite's JavaScript API with the project's own Vite configuration file, not through the `dev` script of `package.json`. Options in that script do not apply. Host, port, `strictPort` and file polling are set on top of the project's configuration, in memory; no file is written. `vite` must be a dependency of the project.
- The development server listens on `0.0.0.0:3000`. Do not change the port in the project configuration.
- Vite rejects requests for host names it does not know. Add the environment's hosts to `server.allowedHosts`: `WODBY_HOSTS` holds them as a JSON array. The boilerplate's `vite.config.ts` does this.
- File watching uses polling, so saved files and new route files are picked up without a restart. The route tree in `src/routeTree.gen.ts` is regenerated by the development server; keep it in Git.
- `NODE_ENV` is `development` here.
- `/.output/`, `/.nitro/` and `/.tanstack/` are kept out of Git status, in addition to the Node.js service's paths.
- The image build's `npm run build` does not run in a workspace.
